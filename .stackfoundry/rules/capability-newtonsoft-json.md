## Rules

- **Never set TypeNameHandling to anything but None on the settings that deserialize Transloadit responses, and never let a caller's configure callback or host defaults turn it on silently. If type names are ever needed, restrict them with an ISerializationBinder allow-list.** Responses come from the network (public API, proxies, a compromised or spoofed endpoint). With TypeNameHandling other than None, a `$type` in the payload makes Json.NET instantiate attacker-chosen types: the classic insecure-deserialization hole (command execution, file deletion). CA2326 flags it; it is off by default in .NET 10 analyzers, so the build will not catch it. Here: src/Transloadit/Serialization/NewtonsoftJsonSerializer.cs NewtonsoftJsonSerializer(Action<JsonSerializerSettings>); src/Transloadit/Serialization/TransloaditSerializerSettings.cs CreateDefault. [nj-typenamehandling, ca2326]
- **Isolate the engine from the host's JsonConvert.DefaultSettings: serialize and deserialize through JsonSerializer.Create(settings) (with a StringWriter/JsonTextReader), not JsonConvert.SerializeObject/DeserializeObject; or, at minimum, set explicitly every setting the wire format depends on (TypeNameHandling = None, DateParseHandling, MaxDepth, DateFormatString, FloatFormatHandling, Formatting). Keep these in TransloaditSerializerSettings.CreateDefault and build the NewtonsoftJsonSerializer settings from it, so the defaults test guards the settings actually used.** JsonConvert.SerializeObject/DeserializeObject call JsonSerializer.CreateDefault(settings), which first applies DefaultSettings and then overrides only the values the passed settings explicitly set; host converters are kept (behind ours). A consuming app that sets JsonConvert.DefaultSettings (TypeNameHandling.All, DateParseHandling.DateTimeOffset, a DateFormatString, a JavaScriptDateTimeConverter) changes how this library reads API responses and writes the signed params on net452/net461 only, so the two engines diverge per host. The settings are also built twice (constructor and CreateDefault); SerializationDefaultsTests only checks CreateDefault. Here: src/Transloadit/Serialization/NewtonsoftJsonSerializer.cs Serialize / Deserialize (JsonConvert calls), constructor (duplicate settings); src/Transloadit/Serialization/TransloaditSerializerSettings.cs CreateDefault; tests/Transloadit.Tests/Tests/SerializationDefaultsTests.cs CreateDefault_Should_ReturnExpectedDefaults. [nj-jsonconvert-src, nj-serializer-src, nj-defaultsettings, nj-create, nj-createdefault]
- **Keep Newtonsoft.Json at 13.0.1 or later and never set MaxDepth to null; leave the 64-level read limit in place.** Before 13.0.1 there was no default depth limit: deeply nested JSON caused StackOverflow or CPU/RAM exhaustion (CVE-2024-21907 / GHSA-5crp-9r3c-p9vr, CVSS 7.5). 13.0.1 made 64 the default for JsonReader and JsonSerializer. Note the asymmetry: Newtonsoft's MaxDepth limits reading only, while System.Text.Json's MaxDepth (64) also limits writing, so a request whose Fields/Ffmpeg dictionaries nest deeper than 64 serializes on net452/net461 but throws JsonException on every other TFM. Since 13.0.1. Here: src/Transloadit/Transloadit.csproj PackageReference Newtonsoft.Json 13.0.1; src/Transloadit/Models/Assemblies/AssemblyRequest.cs Fields (Dictionary<string, object>). [ghsa-5crp, nj-releases, nj-settings-src, nj-reader-src, stj-maxdepth]
- **Give every IsoDateTimeConverter (or any Newtonsoft date formatting) Culture = CultureInfo.InvariantCulture explicitly.** IsoDateTimeConverter.Culture falls back to CultureInfo.CurrentCulture when unset, and the format string is applied with that culture: under th-TH/ar-SA/fa-IR the signed `expires` and pagination dates get a Buddhist/Umm al-Qura year or non-Latin digits and the API rejects the request. Here: src/Transloadit/Serialization/TransloaditContractResolver.cs CreateProperty (TransloaditDateFormatAttribute branch); src/Transloadit/Serialization/DateTimeConverters.cs AuthExpiresDateTimeConverter, PaginationDateTimeConverter. [nj-isodate-src]
  This repo: Already done in all three places; tests/Transloadit.Tests/Tests/Unit/CultureRobustnessTests.cs SerializeAndDeserialize_AreCultureInvariant guards it (only when run on net461 for this engine).
- **Treat request DateTime values as UTC before they reach the formatter: the `expires` format hard-codes `+00:00`, and neither engine converts. Either convert with ToUniversalTime in both engines (DateTimeStyles.AdjustToUniversal on the Newtonsoft IsoDateTimeConverter plus the same in StjDateFormatConverter) or reject non-UTC kinds; change both engines together.** IsoDateTimeConverter only converts to UTC when DateTimeStyles includes AdjustToUniversal/AssumeUniversal; the default RoundtripKind writes the clock time as is. A caller passing AuthParams.Expires = DateTime.Now gets local wall-clock time labelled +00:00, so the signature's expiry is off by the host's UTC offset: rejected as expired east of UTC, valid too long west of it. Here: src/Transloadit/Models/BaseRequests.cs AuthParams.Expires ([TransloaditDateFormat("yyyy'/'MM'/'dd HH:mm:ss+00:00")]); src/Transloadit/TransloaditClient.cs BuildRequest (caller-supplied Expires passed through; default is DateTime.UtcNow). [nj-isodate-src]
- **Parse response timestamps that may lack a zone the same way on both engines: add a Newtonsoft DateTimeOffset converter mirroring StjDateTimeOffsetConverter (InvariantCulture, AssumeUniversal | AdjustToUniversal), or prove the API always sends a zone.** For a DateTimeOffset member, Json.NET falls back to DateTimeOffset.TryParse(s, Culture, DateTimeStyles.RoundtripKind); RoundtripKind has no effect on DateTimeOffset, so a string with no offset gets the machine's local offset. The STJ converter assumes UTC. The current "2020/01/09 12:02:06 GMT" shape parses identically, but any zone-less timestamp is shifted by the host offset on net452/net461 only. Here: src/Transloadit/Models/Assemblies/AssemblyResponse.cs ExecutionStart, Created, StartDate, NotifyStart, LastJobCompleted; src/Transloadit/Models/Templates/TemplateResponse.cs Created, Modified, LastUsed; src/Transloadit/Serialization/StjConverters.cs StjDateTimeOffsetConverter (the STJ behaviour to match). [nj-reader-src, ms-dto-tryparse]
- **Decide one runtime shape for untyped (object / Dictionary<string, object>) response members and enforce it on both engines: set DateParseHandling = DateParseHandling.None on the Newtonsoft settings, and either convert nested JObject/JArray to Dictionary<string, object>/List<object> or document that net452/net461 consumers get JToken.** Json.NET reads object-typed values as boxed string/long/double/bool/DateTime and nested values as JObject/JArray, and with the default DateParseHandling.DateTime turns any ISO-8601-looking string into a DateTime (the maintainer will not change this, issue #862). StjInferredTypeConverter returns strings and Dictionary/List. A consumer's `fields["meta"] as Dictionary<string, object>` is null on net461, and a field value "2024-01-01T00:00:00Z" is a DateTime there and a string elsewhere. Here: src/Transloadit/Models/Assemblies/AssemblyResponse.cs Fields, Meta, UserMeta, ParentAssemblyStatus; src/Transloadit/Models/Templates/TemplateResponse.cs Steps; src/Transloadit/Models/Billing/BillingPlan.cs Tiers, CustomRobotFactors; src/Transloadit/Serialization/StjConverters.cs StjInferredTypeConverter (doc comment claims it matches Newtonsoft). [ms-migrate, nj-dateparsehandling, nj-issue-862, nj-settings-src]
- **Make every response value-type member the API can send as null nullable; do not read a passing net461 run as proof that a null is handled.** With NullValueHandling.Ignore (this repo's setting), Json.NET does not throw on a JSON null for a non-nullable value type: it leaves the default (DateTimeOffset.MinValue, 0, false), silently corrupting data. System.Text.Json throws for the same input. The same model fails loudly on net8 and returns wrong data on net461. Here: src/Transloadit/Models/Assemblies/AssemblyResponse.cs Created (non-nullable DateTimeOffset); src/Transloadit/Models/Templates/TemplateResponse.cs Created, Modified; src/Transloadit/Models/Billing/BillingPlan.cs Created, Modified. [ms-migrate]
- **When adding a member typed as an abstract base (another RobotBase collection, a nested credentials base), add a value-level golden case asserting a derived-only property; a green net461 run says nothing about STJ.** Json.NET serializes by runtime type automatically; System.Text.Json serializes against the declared type unless told otherwise, dropping every robot-specific parameter. The Newtonsoft leg hides this bug class rather than catching it. Here: src/Transloadit/Models/Robots/RobotBase.cs (steps are Dictionary<string, RobotBase>); src/Transloadit/Serialization/StjConverters.cs StjPolymorphicRobotConverterFactory; tests/Transloadit.Tests/Tests/Models/AutoPopulatedRobotGoldenTests.cs PopulatedRobot_MatchesCrossProviderGolden. [ms-migrate]
- **Map models only with the provider-neutral Transloadit* attributes; never put [JsonProperty], [JsonConverter], [JsonIgnore] or other Newtonsoft attributes on library models.** DefaultContractResolver honours Newtonsoft attributes, so they take effect on net452/net461 only; System.Text.Json ignores them, and the JSON key or converter differs by target framework. Converter precedence also differs between the engines (property attribute, then type attribute, then settings in Json.NET). Here: src/Transloadit/Serialization/TransloaditContractResolver.cs CreateProperty (maps TransloaditJsonName/JsonIgnore/BooleanToInt/DateFormat); src/Transloadit/Models/**. [ms-migrate]
  This repo: readme.md ("Do not use native serializer attributes") and .claude/skills/add-credentials/SKILL.md say this. CLAUDE.md (Robots section) and .claude/agents/csharp-build-reviewer.md still say to use [JsonProperty("snake_case_name")]: stale, see questions.
- **Give every Newtonsoft converter that has an STJ twin the same read coercions and null handling, and test each input shape on both legs.** BooleanToIntConverter.ReadJson uses Convert.ToInt32(reader.Value): a JSON string "true"/"false" throws FormatException, which StjBooleanToIntConverter.ReadBoolean accepts. A JSON null becomes 0, so false, where StjNullableBooleanToIntConverter returns null for bool?. The theory BooleanToInt_ReadsNumberStringAndBoolTokens covers neither shape. Here: src/Transloadit/Serialization/BooleanToIntConverter.cs ReadJson; src/Transloadit/Serialization/StjConverters.cs StjBooleanToIntConverter.ReadBoolean; tests/Transloadit.Tests/Tests/Unit/ResponseDeserializationTests.cs BooleanToInt_ReadsNumberStringAndBoolTokens. [ms-convert-toint32]
- **Bump the test project's Newtonsoft.Json in lock-step with the library's (equal or higher, never lower).** The test project references both the library (which depends on Newtonsoft.Json on net461) and Newtonsoft.Json directly; a lower direct pin is a package downgrade (NU1605), which the .NET SDK treats as an error, and it would test against a different version than ships. Here: tests/Transloadit.Tests/Transloadit.Tests.csproj PackageReference Newtonsoft.Json 13.0.1; src/Transloadit/Transloadit.csproj PackageReference Newtonsoft.Json 13.0.1. [nu1605]

## Bug categories

| Category | Look for | Failure |
|---|---|---|
| `insecure-type-name-handling` (blocker) | TypeNameHandling set to anything but None (settings, configure callback examples in readme, tests); a missing ISerializationBinder where type names are used. | Attacker-controlled `$type` in an API response instantiates arbitrary types: remote code execution or file deletion in the consuming app. [ca2326, nj-typenamehandling] |
| `host-default-settings-leak` (confirm) | JsonConvert.SerializeObject/DeserializeObject (or JToken.ToObject/FromObject) in library code; a wire-relevant setting left unset on the library's JsonSerializerSettings. | The consuming app's JsonConvert.DefaultSettings changes how responses are parsed (dates, type names, extra converters) and how signed params are written, on net452/net461 only. [nj-jsonconvert-src, nj-serializer-src, nj-defaultsettings] |
| `culture-sensitive-date-format` (blocker) | new IsoDateTimeConverter without Culture = CultureInfo.InvariantCulture; DateTime.ToString(format) without a provider in serialization code. | Signed `expires`/pagination dates are written with a locale calendar or digits; the API rejects the signature. [nj-isodate-src] |
| `local-time-labelled-utc` (confirm) | Request DateTime members formatted with a literal `+00:00` or `Z` and no ToUniversalTime/AdjustToUniversal; callers passing DateTime.Now. | `expires` is shifted by the host's UTC offset: requests are rejected as expired, or signatures stay valid longer than intended. [nj-isodate-src] |
| `zone-less-timestamp-local-offset` (confirm) | DateTimeOffset/DateTime response members parsed by Json.NET's built-in reader with no converter, where the API may omit the zone. | Timestamps are shifted by the machine's local offset on net452/net461, while STJ treats them as UTC. [nj-reader-src, ms-dto-tryparse] |
| `untyped-member-shape-divergence` (confirm) | object / Dictionary<string, object> response members; tests asserting only "not JsonElement" for nested values; DateParseHandling left at default. | Consumers get JObject/JArray and DateTime on net452/net461 but Dictionary/List and string elsewhere; casts return null or throw InvalidCastException depending on TFM. [ms-migrate, nj-dateparsehandling, nj-issue-862] |
| `silent-null-into-value-type` (confirm) | Non-nullable DateTimeOffset/int/double/bool response members for fields the API can return as null (lifecycle fields of in-progress or failed assemblies). | Json.NET with NullValueHandling.Ignore leaves the default value (0001-01-01, 0, false) with no error: wrong data on net461, exception on STJ. [ms-migrate] |
| `converter-twin-divergence` (confirm) | A Newtonsoft JsonConverter and its STJ counterpart that differ in accepted token types, null handling, culture or DateTimeStyles (BooleanToIntConverter vs StjBooleanToIntConverter, IsoDateTimeConverter vs StjDateFormatConverter). | The same API payload parses on one TFM and throws, or yields a different value, on another. [ms-convert-toint32, nj-isodate-src] |
| `native-newtonsoft-attribute` (blocker) | [JsonProperty], [JsonConverter], [JsonIgnore], [JsonObject] from Newtonsoft.Json on library models or robots. | The JSON key or converter differs by target framework; the API ignores the misnamed parameter on STJ frameworks. [ms-migrate] |

## Performance

- Create the contract resolver once and reuse it: DefaultContractResolver caches contracts per instance, and a new resolver repeats the reflection on every call. Here a resolver lives per NewtonsoftJsonSerializer, which lives per TransloaditClient, so a client created per request pays reflection every time. Here: src/Transloadit/Serialization/NewtonsoftJsonSerializer.cs constructor (new TransloaditContractResolver()); src/Transloadit/TransloaditClient.cs CreateDefaultSerializer. [nj-performance]

## Security

- Stakes are auth and data integrity, exposure public: responses are untrusted input. Keep TypeNameHandling None, keep the 13.0.1+ MaxDepth limit, and do not inherit host DefaultSettings (see rules). No advisory affects 13.0.1 to 13.0.4; the only Newtonsoft.Json advisory is CVE-2024-21907 (< 13.0.1). Here: src/Transloadit/Serialization/NewtonsoftJsonSerializer.cs. [ghsa-5crp, gh-advisories, ca2326]
- The signature is computed over the exact params string the serializer produced and that same string is sent, so engine formatting differences do not break signatures. Value differences do: a mis-formatted or mis-zoned `expires` is signed as is. Here: src/Transloadit/TransloaditClient.cs BuildRequest. [nj-isodate-src]

Applies to: client. Versions in use: 8.0.5 (NuGet package) (src/Transloadit/Transloadit.csproj, PackageReference for netstandard2.0, net462, net472, net48, net5.0, net6.0, net7.0); 8.0.x (in-box) (net8.0 TFM: whatever .NET 8 runtime the consumer runs); 9.0.x (in-box) (net9.0 TFM: whatever .NET 9 runtime the consumer runs); 10.0.x (in-box) (net10.0 TFM: whatever .NET 10 runtime the consumer runs).

## Rules

- **Serialize the root object by its runtime type, and send every member whose declared type is a base class through runtime-type dispatch. STJ serializes nested values by their declared type. Newtonsoft serializes by runtime type.** Without that dispatch, STJ writes only the base-class members of a Dictionary<string, RobotBase> value and silently drops every robot parameter. The request is still accepted, so the API processes the wrong instructions, and only on STJ TFMs. StjPolymorphicRobotConverterFactory.CanConvert matches only abstract RobotBase subtypes. A new member declared as another abstract base (for example a nested CredentialsRequestBase), or as a non-abstract class with subclasses, is not covered. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs SystemTextJsonSerializer.Serialize (value.GetType()); src/Transloadit/Serialization/StjConverters.cs StjPolymorphicRobotConverterFactory.CanConvert / StjPolymorphicRobotConverter.Write; src/Transloadit/Models/Robots/RobotBase.cs RobotBase. [stj-polymorphism, stj-migrate]
- **Keep the re-dispatch converter for robot steps. Do not replace it with [JsonPolymorphic]/[JsonDerivedType], and never set TypeDiscriminatorPropertyName to a name a model already uses ("robot", "type").** Attribute polymorphism needs every derived type registered: an unregistered robot (including a user subclass) throws NotSupportedException. It also writes a "$type" discriminator the Transloadit API does not define. A discriminator named "robot" collides with RobotBase.Robot: STJ 8 writes the key twice, and from .NET 10 serializing the type throws InvalidOperationException, so behaviour would differ by TFM. Since property-name conflict validation: .NET 10. Here: src/Transloadit/Models/Robots/RobotBase.cs RobotBase.Robot; src/Transloadit/Models/Credentials/CredentialsRequest.cs CredentialsRequestBase.Type. [stj-polymorphism, break-10-propname]
- **In every JsonConverter<T> for a value type, handle JsonTokenType.Null in Read explicitly, either by throwing JsonException or by applying the agreed parity behaviour. Do not let reader.GetString() feed null into Parse.** STJ passes the Null token to custom converters of non-nullable value types. GetString() returns null for it, so DateTimeOffset.Parse(null) throws ArgumentNullException with no JSON path, and GetBoolean() on Null throws InvalidOperationException. Per the docs, the Newtonsoft engine with NullValueHandling.Ignore leaves the default value instead, so a response with "created": null fails only on STJ. Here: src/Transloadit/Serialization/StjConverters.cs StjDateTimeOffsetConverter.Read; src/Transloadit/Serialization/StjConverters.cs StjDateFormatConverter.Read; src/Transloadit/Serialization/StjConverters.cs StjBooleanToIntConverter.ReadBoolean; src/Transloadit/Models/Templates/TemplateResponse.cs TemplateModel.Created / Modified / RequireSignatureAuth. [stj-converters, stj-getstring, stj-migrate]
- **In converters, use the TryGet* reader methods and throw JsonException for a token shape you cannot map. Do not let GetInt32, GetString or DateTime(Offset).Parse throw out of Read.** Only JsonException and NotSupportedException get the JSON path added by the serializer. Utf8JsonReader.GetInt32 throws FormatException for 1.0, exponent notation or out-of-range values, and InvalidOperationException for a non-number token. Callers that catch JsonException around a response call miss these exceptions, and the error does not say which field failed. Here: src/Transloadit/Serialization/StjConverters.cs StjBooleanToIntConverter.ReadBoolean (reader.GetInt32()); src/Transloadit/Serialization/StjConverters.cs StjDateTimeOffsetConverter.Read. [stj-converters, stj-getint32]
- **Do not assume STJ coerces JSON token types the way Newtonsoft does. For a response field the API may send in more than one shape, add a targeted coercion: a converter applied by the modifier, or JsonTypeInfo.NumberHandling for one type. Never flip a global option silently.** STJ rejects a number or bool for a string property ("could not be converted to System.String") and a quoted number for a numeric property. Newtonsoft accepts both. One unexpected shape fails the whole response deserialization on STJ TFMs only. A global NumberHandling change would also alter the request wire format the golden tests pin. Here: src/Transloadit/Models/BaseResponses.cs ResponseBase http_code (int?); src/Transloadit/Models/Templates/TemplateResponse.cs TranscodingResultExpiry / AssemblyStatusExpiry (string); src/Transloadit/Models/Assemblies/AssemblyResponse.cs numeric fields. [stj-migrate, stj-custom-contracts]
- **Format and parse every wire date in a converter with an explicit format and CultureInfo.InvariantCulture. Never let a DateTime/DateTimeOffset reach STJ's built-in date converter on the request path, and keep the global lenient DateTimeOffset reader for responses.** STJ's built-in reader and writer support only the ISO 8601-1:2019 extended profile: a 'T' separator, trimmed fractions, no ' GMT' suffix. The signed `expires` value must be "yyyy/MM/dd HH:mm:ss+00:00" and pagination dates "yyyy-MM-dd HH:mm:ss", so a built-in-formatted value is rejected or changes the signed payload. Responses such as "2020/01/09 12:02:06 GMT" throw JsonException in the built-in reader. Here: src/Transloadit/Models/BaseRequests.cs AuthParams.Expires, PaginationParams.FromDate / ToDate; src/Transloadit/Serialization/StjConverters.cs StjDateFormatConverter, StjNullableDateFormatConverter, StjDateTimeOffsetConverter; src/Transloadit/Serialization/SystemTextJsonSerializer.cs ApplyConverter. [stj-datetime, stj-migrate]
- **Sign exactly the string the serializer produced and send that same string. Never re-serialize, pretty-print or normalize params between signing and sending. In tests, compare JSON structurally, not as raw strings across engines.** STJ's default encoder escapes all non-ASCII characters and HTML-sensitive ASCII as \uXXXX. The current writer source also escapes '+', so `expires` "...+00:00" goes out as "...\u002B00:00", while Newtonsoft writes these characters literally. The meaning is the same, but the bytes differ per TFM. A signature computed over any other serialization of the same object fails authentication. Here: src/Transloadit/TransloaditClient.cs BuildRequest (paramsJson -> SignatureUtilities.CalculateSignature -> params field); tests/Transloadit.Tests/Tests/Models/SerializationGoldenTests.cs Serializes_To_Golden (JToken.DeepEquals). [stj-character-encoding, stj-escaping-source, stj-migrate]
- **Keep StjInferredTypeConverter registered for object-typed members. When you add an object or Dictionary<string, object> member, decide and test which CLR types consumers get on each engine.** Without the converter, STJ stores a boxed JsonElement for every object-typed value, which consumers cannot cast or walk like the Newtonsoft TFMs. Even with it, the documented Newtonsoft behaviour still differs: Newtonsoft returns JObject/JArray for nested values and DateTime for date-like strings, while this converter returns Dictionary/List and string. Here: src/Transloadit/Serialization/StjConverters.cs StjInferredTypeConverter; src/Transloadit/Models/Assemblies/AssemblyResponse.cs Fields / Meta / UserMeta; src/Transloadit/Models/Templates/TemplateResponse.cs Steps; src/Transloadit/Models/Billing/BillingPlan.cs Tiers / CustomRobotFactors. [stj-migrate, stj-converters]
- **Before adding a converter, check converter precedence. The first converter in Options.Converters whose CanConvert returns true wins, the Converters collection beats a type-level [JsonConverter], and a property-level converter beats both. Converters a caller adds through the configure callback come after the library's four.** A user converter for object, RobotBase, AnyOf or DateTimeOffset passed through `configure` is never consulted, and nothing reports that. Inserting a library converter before StjInferredTypeConverter that also matches object would change every untyped member. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs SystemTextJsonSerializer(Action<JsonSerializerOptions>) converter registration order. [stj-converters, stj-migrate]
- **Build JsonSerializerOptions once per serializer. Apply `configure` before first use, never mutate the options afterwards, and reuse one serializer per client.** Options become immutable after the first Serialize or Deserialize call: setters such as MaxDepth then throw InvalidOperationException. The per-type metadata cache, which here includes the reflection-heavy ApplyNeutralAttributes modifier, lives on the options instance, so a new SystemTextJsonSerializer per request rebuilds every contract. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs constructor; src/Transloadit/TransloaditClient.cs MergeOptions / CreateDefaultSerializer. [stj-configure-options, stj-maxdepth]
- **Do not rely on [TransloaditJsonName] alone to make a response property with a non-public setter deserializable. STJ binds only public setters by default, and the modifier adds only non-public properties, not public properties with non-public setters.** TransloaditContractResolver sets Writable = true, so Newtonsoft fills such a property, but STJ leaves it at its default without error. That is harmless for serialize-only members today (RobotBase.Robot, CredentialsRequestBase.Type), but on a response model it is silent data loss on STJ TFMs. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs ApplyNeutralAttributes; src/Transloadit/Serialization/TransloaditContractResolver.cs CreateProperty; src/Transloadit/Models/Robots/RobotBase.cs RobotBase.Robot { get; protected set; }. [stj-migrate, stj-custom-contracts]
- **Use only APIs that exist in System.Text.Json 8.0.5 in shared code. Guard anything newer (AllowDuplicateProperties, JsonSerializerOptions.Strict, JsonSerializerOptions.Web, RespectNullableAnnotations) with #if, and add a golden case proving that net48 and net10.0 still emit the same payload.** netstandard2.0, net462, net472, net48 and net5.0 to net7.0 compile against the 8.0.5 package, so an unguarded call fails the build for those TFMs. A guarded call makes the wire format or the error behaviour depend on the consumer's TFM, which is the divergence the golden tests exist to prevent. Since Web: .NET 9; AllowDuplicateProperties/Strict: .NET 10. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs; src/Transloadit/Transloadit.csproj. [stj-whatsnew-10, stj-configure-options, nuget-stj-805]
- **Keep the System.Text.Json PackageReference conditioned to TFMs whose in-box STJ is older than the package. When the package is bumped, recompute that TFM list and the TRANSLOADIT_NEWTONSOFT list together.** On the .NET 10 SDK, a direct reference on a TFM that already ships the library raises NU1510, and TreatWarningsAsErrors is on here. The 8.0.5 package supports net462, netstandard2.0 and net6.0+, and 10.0.x supports net462, netstandard2.0 and net8.0+. Older .NET Core TFMs (net5.0 today; net5.0 to net7.0 after a bump to 10.x) fall back to the netstandard2.0 asset in an unsupported configuration, which the package flags with a build warning. Here: src/Transloadit/Transloadit.csproj ItemGroup PackageReference System.Text.Json 8.0.5 / PropertyGroup TRANSLOADIT_NEWTONSOFT. [nu1510, nuget-stj, nuget-stj-805]

## Bug categories

| `stj-declared-type-truncation` (blocker) | A new request member declared as an abstract or non-sealed base type other than an abstract RobotBase subtype: a nested CredentialsRequestBase, a List<ImportRobotBase>, a concrete robot property that holds a subclass. | On every STJ TFM only the declared type's members are written, so robot or credential parameters are silently missing from the signed request. The entire response is lost. The Newtonsoft engine (NullValueHandling.Ignore) keeps the default value. [stj-converters, stj-getstring, stj-migrate] |

[stj-converters, stj-getint32] |

## Wiring

- SystemTextJsonSerializer's constructor registers StjAnyOfConverterFactory, StjPolymorphicRobotConverterFactory, StjInferredTypeConverter and StjDateTimeOffsetConverter before `configure` runs, and ApplyNeutralAttributes attaches the BooleanToInt and DateFormat converters per property. Fails as: Without the AnyOf converter, STJ walks AnyOf's public Value and Type properties, and serializing a System.Type throws NotSupportedException. Without the others, robot parameters are dropped, JsonElement leaks into responses, or GMT dates throw.. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs constructor / ApplyNeutralAttributes / ApplyConverter. [stj-converters, stj-custom-contracts]
- A new provider-neutral attribute is honoured in all three places: SystemTextJsonSerializer.ApplyNeutralAttributes, TransloaditContractResolver.CreateProperty, and NeutralConverter in ModelSerializationSnapshotTests. Fails as: One engine ignores the attribute. Because CI never runs net461, the divergence ships unnoticed.. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs ApplyNeutralAttributes; src/Transloadit/Serialization/TransloaditContractResolver.cs CreateProperty; tests/Transloadit.Tests/Tests/Models/ModelSerializationSnapshotTests.cs NeutralConverter. [stj-custom-contracts]
- The TFMs that define TRANSLOADIT_NEWTONSOFT (net452 and net461 in the library; net461 in the test project) are exactly the TFMs the System.Text.Json package cannot serve, and every other TFM either references the package or has STJ in-box. Fails as: A TFM compiled with neither engine fails to build, or tests compile against a different engine than the library on that TFM.. Here: src/Transloadit/Transloadit.csproj; tests/Transloadit.Tests/Transloadit.Tests.csproj; src/Transloadit/Serialization/TransloaditSerializerFactory.cs CreateDefault. [nuget-stj-805]

## Testing

## Performance

- Contract metadata, including the reflection walk in ApplyNeutralAttributes, is cached per JsonSerializerOptions instance and is thread-safe. One serializer per TransloaditClient is right. Do not construct SystemTextJsonSerializer per call, and document that consumers should reuse the client. Here: src/Transloadit/Serialization/SystemTextJsonSerializer.cs; src/Transloadit/TransloaditClient.cs MergeOptions. [stj-configure-options]
- The DateTime(Offset).Parse-based converters are slower than the built-in UTF-8 parsers. That is acceptable here because the Transloadit formats are not ISO 8601. Do not switch to TryGetDateTime-only parsing, which rejects the API's GMT format. Here: src/Transloadit/Serialization/StjConverters.cs StjDateTimeOffsetConverter.Read. [stj-datetime]

## Security

- Pin at least 8.0.5. CVE-2024-43485 (GHSA-8g4q-xg66-9fp4, DoS when deserializing into a type with [JsonExtensionData]) affects 8.0.0 through 8.0.4, and CVE-2024-30105 (GHSA-hh2w-p6rv-4g7w, DoS in DeserializeAsyncEnumerable) affects versions below 8.0.4. The repo calls neither API (grep found no JsonExtensionData or DeserializeAsyncEnumerable). The GitHub Advisory Database lists no later System.Text.Json advisory as of 2026-11-09. Here: src/Transloadit/Transloadit.csproj PackageReference System.Text.Json 8.0.5. [ghsa-43485, ghsa-30105, gh-advisories-stj]
- .NET 8 and .NET 9 reach end of support on 2026-11-10, so the 8.0.x package line gets no more security fixes after that date. On netstandard2.0 and .NET Framework, consumers stay on whatever 8.0.x the package resolves to, and a future STJ 8 advisory would have no patch. The supported line is 10.0.x (.NET 10 LTS, end of support 2028-11-14), which still ships net462 and netstandard2.0 assets. Here: src/Transloadit/Transloadit.csproj. [dotnet-support-policy, nuget-stj]
- Response bodies come from the network and are parsed with default limits. Keep MaxDepth at its default of 64, which is also Newtonsoft's: going past it throws JsonException, and the recursive StjInferredTypeConverter relies on the reader's depth check. Duplicate JSON keys resolve last-wins on every version; rejecting them (AllowDuplicateProperties = false) exists only from .NET 10, so it cannot be uniform across TFMs. Here: src/Transloadit/Serialization/StjConverters.cs StjInferredTypeConverter.Read; tests/Transloadit.Tests/Tests/Unit/MalformedInputTests.cs Deserialize_DeeplyNestedBody_ThrowsInsteadOfCrashing. [stj-maxdepth, stj-migrate, stj-whatsnew-10]
- Authentication depends on the signed params string being byte-identical to the one sent (see the rule on signing). Never install JavaScriptEncoder.UnsafeRelaxedJsonEscaping on an options instance whose output is also rendered into HTML. Inside this library the params only go to the API, so the encoder choice affects bytes, not safety. Here: src/Transloadit/TransloaditClient.cs BuildRequest. [stj-character-encoding]
